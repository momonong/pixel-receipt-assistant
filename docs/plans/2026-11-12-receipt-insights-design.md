# 收據管理與支出分析設計

使用者要求：每種收據標籤不同顏色；一般清單隱藏已刪除及不正常收據，有篩選；原生 App 提供直覺的互動支出分析，支援一般手機與折疊尺寸。使用者已實測接受 0.5.5，並要求開始開發本目標。

## 決策與範圍

沿用 Kotlin/Compose、既有青綠品牌與繁中系統字體、FastAPI/SQLite 與正式帳本金額；新增唯讀彙整，不修改帳目、草稿、照片或推論。這次開發與工程候選不自動涵蓋新版本的合併、推送、正式部署或手機安裝。

比較過網頁 Dashboard、只在手機合計當頁帳目、以及原生頁面配後端完整彙整。採第三種：維持 App 流程，後端對完整範圍計算，沿用確定性整數金額。網頁會跳出 App；當頁合計可能漏掉未載入帳目。

下列細節為承接者依需求作的可逆實作選擇，非使用者逐項指定：

- 收據清單預設「一般」；正常新收件、待核對、已完成及參考成果保留。已刪除、作廢、缺照片、失敗、來源未就緒、結果不確定隱藏，有需處理數量與篩選入口。
- 長期處理中的舊測試：依中央 `created_at` 已超過 24 小時或中央已結束輪詢仍無結果，呈現「等待較久／結果待查詢」並歸需處理。中央時間缺失時不以本機照片建立時間推斷逾期。這僅是顯示分類，不宣稱失敗、不重送或變更原狀態。
- 待確認的刪除、作廢或補名請求保持可見，避免以隱藏暗示已成功；保留原請求與未知結果的查詢流程。
- 篩選用單一入口與可重設的 sheet，提供一般、需處理、全部及單一狀態，顯示目前筆數。返回明細與旋轉後保留目前選擇，不刪除或搬移資料。
- 每種語意狀態有固定、獨立的淡底深字配色；標籤文字同時表達狀態，不能只靠顏色。清單、明細、帳本相同狀態使用相同 token。數量變化不是新的語意狀態。

## 分析的問題與內容

主問題：「這段時間，我自己的支出是多少，主要花在哪裡？」第一版從可靠既有欄位出發：

1. 日期範圍：本月、上月、今年、全部、自訂日曆；主數字是個人支出（自己用＋送人），實付、代買與明列折扣分開說明。
2. 時間趨勢：點日期／月份查看對應已入帳帳目，有文字與前後選取方式，空期間保留零值、不畫假成長。
3. 店家排行：依正式個人支出排序，可點店家查看對應帳目；原始店名不自動合併分店或推測分類。
4. 用途構成：自己用、送人、代買分開；不再次從個人支出扣掉已排除代買，不再次扣除內含折扣。
5. 同期比較採明確的比較日期，沒有基準時不造百分比。未填日期的歷史資料在全部中保留並可查看，期間篩選明示排除筆數。
6. 點選結果使用既有帳目明細，返回分析保留期間、店家、選取日期及捲動位置。

所有金額來自 active confirmed ledger 的既有 `snapshot.calculation`，整數 TWD 元；作廢、草稿、參考圖不計入。頁數不影響摘要；超過支援範圍明確拒絕，不截斷或用浮點數計帳。明列折扣沿用既有定義，不稱市場節省。

## API 契約（開發固定介面）

`GET /v1/spending` 沿用既有認證，參數 `date_from/date_to`、可選成對 `compare_from/compare_to`、`bucket=auto|day|month|year`。回覆：

- `scope=active_confirmed_ledger`, `currency=TWD`, `amount_unit=TWD_YUAN`, `date_from/date_to`, `bucket`, `generated_at`。
- `summary` 包含既有 overview 金額鍵、receipt_count、missing_item_name_count、receipts_missing_item_names。
- `comparison` 為 null 或含比較日期、個人支出／筆數及 `delta_personal_yuan`，同一讀取快照。
- `series` 按時間排序，元素 `{date_from,date_to,label,personal_yuan,receipt_count}`；只包含已占用桶，UI 依真實時間配置間距／補有限範圍零值。auto 近期間為 day，較長為 month，超過 120 個月為 year；最多 1000 桶，超出明確錯誤。
- `merchants` 依支出排序，元素 `{key,name,personal_yuan,receipt_count}`；key 是標準化空值／原始店名的 SHA-256（非憑證），name 可為 null，不自動合併品牌分店。
- `undated_receipt_count/undated_personal_yuan` 表達目前範圍的未填日期部分（series 不虛構日期）；`excluded_undated_receipt_count` 表達期間外缺日期資料。

既有 `GET /v1/ledger` 新增可選 `merchant_key`（64 位 hex）與 `undated_only`；與 q、status、日期、分頁共同在分頁前套用。undated_only 與日期界限同時傳入時回 422。分析明細查詢固定 status=active。舊客戶端行為不變。

## 原生狀態與同步

分析是新增原生目的地，與收件匣、帳本、說明同列；原圖、核對與登入沿用。查詢具請求範圍身分，快速換期間／店家時舊回覆不能覆寫新結果。登入切換取消原查詢，舊 401 不清除新憑證。保存已驗證摘要與範圍、更新時間到獨立 AtomicFile（私有 cacheDir，最多 512 KiB 回應）；不將分析塞入收據索引。損壞或過大的衍生快取不能阻止收據讀寫。離線顯示上次資料及過期提示，換範圍不顯示不屬於該範圍的數字。入帳、作廢或補名後使分析過期並重取；未知作廢結果不宣稱刷新完成。

## 介面與驗證

採 design-taste app run 的 Pastel consumer（seed 203285571），保留既有 palette/type；狀態淡色標籤、白色列表面，分析主資料用青綠。原產品收據圖、中文品項、個人／代買的差別是識別，不新增玻璃或行銷裝飾。UI/UX finance 查詢的 glass/marketing 建議不適合既有原生流程，未採用；採命中的 Finance Tracker 與 Compose 自適應、觸控及可及性原則。

一般手機單欄；600dp 以上依可用欄寬及字級安排雙欄，圖表與文字不足空間時回單欄。48dp 觸控、文字對比 4.5:1、選取狀態可由文字及 semantics 辨識；不更動既有亮色主題，不新增字體或圖表依賴。圖表是實際數據繪圖，金額刻度與文字同源。

必要證據：完整後端範圍、作廢、代買、內含折扣、零值、缺日期、超大金額／範圍與分頁；原生篩選可恢復、狀態配色與對比；查詢競態／離線／登入及作廢過期；320dp 150% 字級、390dp、600dp、840dp 與短橫向的真正 Compose 畫面及操作。既有資料與未提交工作保留。
