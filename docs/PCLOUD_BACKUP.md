# pCloud 加密備份與保留政策

PixelReceipt 的異機備份採「每天建立完整備份，驗證後保留最新一份」。
本文件說明已核定的維運流程；repository 只提供可重用的
[快照／驗證／還原工具](../deploy/receipt_backup.py)。主機專用安裝器、排程、
帳戶識別與實際部署收據保存在私人維運目錄，不隨 Git 發布。

## 每日備份

排程為每天 04:00（Asia/Taipei）。主機關機錯過執行時，使用 systemd persistent
計時器於恢復後補執行。流程依序為：

1. 以帳本資料 owner 使用 SQLite backup API 建立一致快照，包含已提交 WAL。
2. 複製快照引用的原圖與認證檔，核對 DB integrity、foreign keys、圖片數量、大小與 SHA-256。
3. 將快照及必要操作設定打包，在主機上以 rclone crypt 加密後上傳至專屬 pCloud 資料夾。
4. 完整下載並解密新備份，核對 SHA-256，在全新私有目錄執行還原。
5. 比較所有業務資料列與原圖；還原副本的手機及瀏覽器 session 必須清空。
6. 新備份通過上述驗證後，才刪除前一個已知雲端備份，最後移除本次本機暫存。

穩定狀態為一份可還原的雲端備份、本機不留每日完整副本。備份、下載或驗證失敗時，
會保留先前有效副本及本次狀態；因此失敗期間可能暫存兩份雲端檔案與本機工作資料。
只有最新一份表示沒有多日歷史回復能力，不應將它當作長期版本封存。

## 備份內容

包含中央帳本、草稿、核對歷史、收件／工作／事件紀錄、所有快照引用的原圖及帳本認證檔。
必要操作設定與相容版本的快照工具一併保存，用於復原核對。

這不是整機映像：共用 API Broker 的資料庫與供應商金鑰、反向代理、其他服務和 APK
二進位不包含在這份備份。操作設定是復原參考，不能直接覆蓋新主機的現行設定。
未被 DB 引用的照片不會由此流程自動刪除；正式原圖及帳本也不屬於保留政策的清理範圍。

## 加密、憑證與恢復設定

使用獨立 rclone remote 綁定專屬資料夾，再以 crypt remote 加密內容。
如保留可讀的備份日期檔名，檔名不代表內容未加密。

pCloud 授權與 crypt 解密設定須保存在私有 `0600` 設定檔，父目錄為 `0700`，
並在另一台可信任裝置保留獨立復原副本。它們不能只存在被備份的同一台主機，
也不能只放進需要該密鑰才能解開的備份中。rclone 的設定密碼欄位是可逆混淆，
設定檔本身仍需檔案權限保護；不要放入 Git、URL、指令參數或日誌。

本機快照工具輸出的目錄未加密；在離開主機前完成加密是雲端維運層的責任。
詳見 [rclone crypt 官方文件](https://rclone.org/crypt/)。

## 中斷恢復與清理邊界

- 單一鎖保證同時只有一個備份作業。
- 每次使用唯一物件名稱並保存階段、大小、雜湊及還原結果。
- 上傳或刪除結果未知時，先列出並核對同一物件，再續接原作業；不因重啟改用新名稱盲目重送。
- 雲端出現非預期檔案、下載雜湊不符或還原失敗時停止清理；不執行全資料夾 `sync` 或 `purge`。
- pCloud 自己的版本／垃圾桶可能另保留歷史檔案；此流程不清空帳號垃圾桶或其他資料夾。
- 清理主機舊快照前，重新下載最新雲端備份並核對完整雜湊，逐一核對預先列冊的舊目錄，
  拒絕符號連結、特殊檔與連到正式資料的 hardlink。
- 刪除只限已核對的舊快照目錄；保留部署收據、正式資料與其他服務。未來部署產生的
  新回復快照要在該次部署驗證後另行列冊，不能用萬用字元清掉未知路徑。

## 還原與升級

使用另一台可信任裝置上的復原設定，經 crypt remote 下載解密到新的私有目錄。
先核對最新成功紀錄中的 SHA-256，解包時拒絕路徑逃逸、連結及特殊檔；再依
[新目錄還原步驟](ASUS_DEPLOYMENT.md#備份驗證與新目錄還原)執行 `verify` 與 `restore`。

還原只寫新目錄，清空復原副本中的舊 session，並核對業務資料列與原圖。
正式資料切換須先驗證相容 release、停止專屬寫入者並保留現行資料；不能在服務寫入中
覆蓋 live 目錄，也不能同時啟動兩個正式帳本寫入者。

DB schema 升級時，同步確認備份工具支援新 schema，執行新版本完整還原演練。
服務顯示 active 或雲端顯示一個檔案都不等於備份成功；應查閱最近一次 `VERIFIED`
紀錄、還原證據與下次排程時間。部署與帳務人工接受仍分別留證。
